# Capsule — an agent that remembers its own mistakes

Built for the Sibyl Labs Hackathon (Sep 1–10, 2026).

## What this is

Capsule is a troubleshooting assistant with persistent memory of its own past failures **and** past successes. When it hits a problem, it checks whether it's about to repeat an action that has already failed under similar conditions — and if so, it refuses to recommend that action and surfaces the verified fix instead, pulled directly from memory rather than re-generated by the model. It also checks whether a proven, previously successful action applies, and prefers that over inventing a new approach.

Memory isn't a chat log here. It's two structured record types, and a belief-revision mechanism connecting them:

- **Scar** — an action that failed, why it failed, and the real fix. Actively blocks that action from being recommended again.
- **Ability** — an action that succeeded. Reinforced with more confidence and evidence every time it succeeds again.

Scars aren't permanent. If a "dangerous" action later succeeds under different conditions, that counts as contradicting evidence. After two pieces of contradicting evidence, the scar flips from `active` to `overridden` — and a new Ability is created, explicitly linked back to the scar it contradicted (`supersedes_scar`). Further repeated success reinforces that linked ability's confidence, not just the scar's counter. After enough contradicting evidence, the scar is formally archived out of Sibyl's WARM tier entirely.

This is the part of the system doing the most conceptual work: memory here isn't a fixed rulebook, it's a set of beliefs that strengthen, weaken, and get replaced as evidence accumulates — and the historical relationship between an old belief and what replaced it is preserved, not discarded.

## Where memory is load-bearing

Every decision the agent makes is gated by real database reads, and every outcome writes back to that same database. No part of this is decorative.

- `src/memory_client.py` — all Sibyl reads/writes live here.
  - `find_relevant_scars()` and `find_relevant_abilities()` query Sibyl before every decision.
  - `create_scar()`, `create_ability()`, `reinforce_ability()`, and `bump_scar_evidence()` are the only places new memory gets written.
  - `bump_scar_evidence()` contains the full lifecycle: increments evidence, flips a scar to `overridden` at 2 contradictions (creating a linked ability), reinforces that linked ability on further contradictions, and calls Sibyl's native `archive_entity()` at 4 contradictions to formally retire the scar from WARM.
- `src/agent.py` — `handle_situation()` is the decision step: it calls `find_relevant_scars()` **and** `find_relevant_abilities()` first, and the prompt sent to the LLM is built entirely from whatever comes back. If nothing is retrieved, the model reasons with no prior context at all — visible directly in the terminal as `Scars consulted: none` / `Abilities consulted: none`.
- **The fix text itself is never generated by the LLM.** `handle_situation()` prints each blocked scar's `real_fix` field straight from the database record, deterministically. Early testing showed the model would occasionally paraphrase or blend fields from different scars when asked to restate them in its own words — what's shown as "the fix" on screen is always the literal stored value, never a language-model reconstruction of it. The same applies to an ability's confidence and evidence numbers: printed directly from the record, not from the model's summary of it.

### Run the deletion test yourself

This is the actual proof, not a claim:

```bash
python src/demo.py --with-memory
```
Agent already knows about a past failure, avoids it, cites the fix.

```bash
python src/demo.py --without-memory
```
Same agent, same situation, pointed at a brand-new empty database (a disposable temp-directory db — your real memory file is never touched). It reasons blind, fails the same way, creates a new scar from that failure, then correctly avoids it on the next call — because it just learned it, not because it was told to.

Delete `memory/capsule.db` entirely and the agent has no scars, no abilities, no history. It will repeat any mistake it hasn't personally made yet in that fresh database. That's the test.

### See the full belief-revision arc

```bash
python src/demo_override.py
```
Shows a scar being contradicted twice (flips to `overridden`, creates a linked ability), then contradicted a third time (that ability's confidence climbs from 0.60 to 0.70), then a fresh call where the agent actively recommends the once-blocked action — citing both the ability that now supports it and the scar it overrode.

## Seed data — where the memory comes from

Two sources, both verifiable:

- **3 scars sourced from real, closed, resolved GitHub issues** (llama-cpp-python #216, #686; peft #2171) — each one is a documented case where someone tried an obvious fix, it failed, and the actual maintainer-confirmed root cause was something else. Every `real_fix` field in these three scars is a paraphrase of an actual maintainer or reporter comment, not invented.
- **5 scars from my own documented mistakes**, made while building a previous hackathon project (real dtype bugs, GitHub Actions gotchas, MCP tool parameter mismatches — the kind of failure every developer using AI coding tools has hit more than once).

`seed_data/scars.json` is the raw data. Run `python src/memory_client.py` to load it into a fresh Sibyl database, or `python src/reset_memory.py` to wipe any existing database and reload cleanly (useful before a demo recording, so old test data doesn't show up on camera).

## Architecture

```
User situation
      |
      v
find_relevant_scars() + find_relevant_abilities()  --> Sibyl FTS5 search, keyword-by-keyword
      |
      v
LLM reasons, given ONLY what memory actually returned
      |
      v
Decision: block (active scar) / prefer (proven ability) / reconsider (overridden scar) / free reasoning
      |
      v
Verified fix / ability data printed from the database, not the model
      |
      v
[the action is actually attempted]
      |
      v
Outcome observed
      |
      +--> failure, no existing scar matched --> new SCAR created
      +--> failure, matches existing active scar --> evidence_for++
      +--> success, no existing ability matched --> new ABILITY created
      +--> success, matches existing ability --> ABILITY reinforced (confidence, evidence up)
      +--> success, contradicts an ACTIVE scar --> evidence_against++
             |
             +--> at 2 contradictions --> scar becomes OVERRIDDEN, linked ability created
             +--> beyond 2 --> linked ability reinforced further
             +--> at 4 contradictions --> scar ARCHIVED out of WARM
```

Sibyl's tiers, as actually used here:
- **WARM** (`set_entity` / `get_entity`) — every active scar and ability lives here.
- **COLD** (`write_event`) — every decision the agent makes is logged, regardless of outcome, for a full audit trail.
- **ARCHIVE** (`archive_entity`) — scars that have accumulated enough contradicting evidence are formally retired here, out of active consideration but not destroyed.
- HOT and REFERENCE are not currently used — kept the scope to what the demo actually needs rather than using every tier for its own sake.

## Known limitations, stated honestly

- **Retrieval is keyword-based FTS5, not semantic.** `find_relevant_scars()` and `find_relevant_abilities()` extract keywords and search Sibyl one at a time (Sibyl's `search_entities()` ANDs every token by default with no built-in OR mode, confirmed from the SDK's own source — so multi-keyword matching is done in Python, not delegated to a single query). This is a deliberate trade-off: Sibyl's own architecture uses no vector database and no embeddings, and this project follows that same design rather than bolting on a separate embedding model. The consequence is that retrieval matches on literal word overlap, not underlying semantic similarity.
- **Outcomes are reported, not independently observed.** `try_action_and_learn()` takes the outcome (`success`/`failure`) as an argument rather than Capsule executing a real tool call and observing the result itself. The interface between "agent proposes an action" and "the real world confirms what happened" is currently the caller, by design — keeping the memory mechanism the thing being demonstrated, rather than building a general-purpose shell-execution sandbox.
- **The LLM's free-text reasoning is not always internally consistent about scar status.** An `overridden` scar has occasionally still been described as something to "avoid" in the model's prose, depending on sampling. This is exactly why the fix text, override status, and ability confidence are all printed as separate, deterministic lines straight from the database rather than trusted to the model's summary. Running with `temperature=0` reduces inconsistency significantly. Treat the printed data lines, not the model's prose, as the source of truth in any test run.

## Stack

- **Sibyl Memory** (`sibyl-memory-client`) — all persistence, WARM + COLD + ARCHIVE tiers.
- **Groq API** (`openai/gpt-oss-20b`) — reasoning engine, `temperature=0` for consistency.
- Python, no frontend — the terminal output is the interface, deliberately, to keep the memory mechanism visible and unobscured by UI.
