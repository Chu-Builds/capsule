# Capsule: an agent that remembers its own mistakes

Built for the Sibyl Labs Hackathon (Sep 1–10, 2026).

## What this is

Capsule is a troubleshooting assistant with persistent memory of its own past failures. When it hits a problem, it checks whether it's about to repeat an action that has already failed under similar conditions — and if so, it refuses to recommend that action and surfaces the verified fix instead, pulled directly from memory rather than re-generated by the model.

Memory isn't a chat log here. It's two structured record types:

- **Scar** — an action that failed, why it failed, and the real fix. Actively blocks that action from being recommended again.
- **Ability** — an action that succeeded. Reinforces confidence in that approach.

Scars aren't permanent. If a "dangerous" action later succeeds under different conditions, that counts as contradicting evidence. After enough of it, the scar flips from `active` to `overridden` — the agent can reconsider the action, while the record still remembers why it was originally flagged. This is the part of the system doing the most conceptual work: memory here isn't a fixed rulebook, it's a belief that updates when contradicted.

## Where memory is load-bearing

Every decision the agent makes is gated by a real database read, and every outcome writes back to that same database. No part of this is decorative.

- `src/memory_client.py` — all Sibyl reads/writes live here. `find_relevant_scars()` queries Sibyl before every decision. `create_scar()`, `create_ability()`, and `bump_scar_evidence()` are the only places new memory gets written.
- `src/agent.py` — `handle_situation()` is the decision step: it calls `find_relevant_scars()` first, and the prompt sent to the LLM is built *from* whatever comes back. If nothing is retrieved, the model reasons with no prior context at all — you can see this directly in the terminal output as `Scars consulted: none`.
- **The fix text itself is never generated by the LLM.** `handle_situation()` prints each blocked scar's `real_fix` field straight from the database record, deterministically, specifically because early testing showed the model would occasionally paraphrase or blend fields from different scars when asked to restate them in its own words. What's shown as "the fix" on screen is always the literal stored value, not a language-model reconstruction of it.

### Run the deletion test yourself

This is the actual proof, not a claim:

```bash
python src/demo.py --with-memory
```
Agent already knows about a past failure, avoids it, cites the fix.

```bash
python src/demo.py --without-memory
```
Same agent, same situation, pointed at a brand-new empty database (a disposable temp-directory db — your real memory file is never touched). It reasons blind, fails the same way, creates a new scar from that failure, then correctly avoids it on the next call — because it just learned it, not because it was told to.

Delete `memory/capsule.db` entirely and the agent has no scars, no abilities, no history. It will repeat any mistake it hasn't personally made yet in that fresh database. That's the test.

## Seed data — where the memory comes from

Two sources, both verifiable:

- **3 scars sourced from real, closed, resolved GitHub issues** (llama-cpp-python #216, #686; peft #2171) — each one is a documented case where someone tried an obvious fix, it failed, and the actual maintainer-confirmed root cause was something else. Every `real_fix` field in these three scars is a paraphrase of an actual maintainer or reporter comment, not invented.
- **5 scars from my own documented mistakes**, made while building a previous hackathon project (real dtype bugs, GitHub Actions gotchas, MCP tool parameter mismatches — the kind of failure every developer using AI coding tools has hit more than once).

`seed_data/scars.json` is the raw data. Run `python src/memory_client.py` to load it into a fresh Sibyl database.

## Architecture

```
User situation
      |
      v
find_relevant_scars()  --> Sibyl FTS5 search, keyword-by-keyword
      |
      v
LLM reasons, given ONLY what memory actually returned
      |
      v
Decision: block (active scar) / reconsider (overridden scar) / free reasoning
      |
      v
Verified fix printed from the database, not the model
      |
      v
[if the action is actually attempted]
      |
      v
Outcome observed --> reinforce existing scar, override it with contradicting
                      evidence, or create a brand new scar/ability
```

Sibyl's five tiers, as actually used here:
- **WARM** (`set_entity` / `get_entity`) — every scar and ability lives here.
- **COLD** (`write_event`) — every decision the agent makes is logged, regardless of outcome, for a full audit trail.
- HOT, REFERENCE, ARCHIVE are not currently used — kept the scope to what the demo actually needs rather than using every tier for its own sake.

## A known limitation, stated honestly

The LLM's free-text reasoning is not always internally consistent about scar status (an `overridden` scar occasionally still gets described as something to "avoid" in the model's prose, depending on sampling). This is why the fix text and the override status are both printed as separate, deterministic lines straight from the database rather than trusted to the model's summary — the terminal output is correct even when the model's phrasing is momentarily sloppy. Running with `temperature=0` reduces this significantly but doesn't guarantee it disappears entirely; treat the printed data lines, not the model's prose, as the source of truth in any test run.

## Setup

```bash
python -m venv venv
source venv/Scripts/activate   # Git Bash on Windows
pip install -r requirements.txt
```

Create `.env`:
```
GROQ_API_KEY=your_key_here
```

Load seed data:
```bash
python src/memory_client.py
```

Run the core demo:
```bash
python src/demo.py --with-memory
```

## Stack

- **Sibyl Memory** (`sibyl-memory-client`) — all persistence, WARM + COLD tiers.
- **Groq API** (`openai/gpt-oss-20b`) — reasoning engine.
- Python, no frontend — the terminal output is the interface, deliberately, to keep the memory mechanism visible and unobscured by UI.
